# System architecture

Flow: browser composer → `population-experiment.js` deterministic parser or `/api/interpret-experiment` → strict `riose-experiment-intent/v1` validation → review/confirmation → `worker-protocol.js` → module Worker → deterministic JS `FarmEngine` paired arms from one snapshot/seed → daily aggregate rows and compact population observations → local `run-history.js` manifest/replay and JSON export → DOM grid, chart, inspector.

`experiments.html` retains the prior form-based workflow via `experiments-app.js`; `product.html` is a separate V2 entry point. No map or farm scene is used. Server provider credentials are loaded from existing environment configuration only. Worker protocol has a versioned `populationCompare` command and progress messages. The observation payload is `riose-population-observations/v1-compact-history`; selected animal history is expanded client-side. Checkpoints are day 0/1/7/15/30/60/90/180/final, bounded by requested duration. Per checkpoint animal state includes ID, name, weight, initial weight, energy, thirst, action, patch; only final checkpoint currently carries compact history tuples. `patch` is engine pasture-stock index, not geography.

Population output uses JS because native Rust/WASM scenario comparison is aggregate-only. Existing JS/Rust parity paths remain unchanged. Upgrade native output only behind versioned contract and parity tests.
