# AI orchestration

V4 local workflows work without a provider. Reuse P3-009's deterministic prompt draft and BEH-016's read-only evidence assistant. Proposed future tools are exact, server/client-validated schemas: list models, get applicability, create draft, validate, compare, sensitivity, conditional cost, inspect results, explain provenance.

Execution tools are never exposed to a model as autonomous authority: model proposals are validated, shown for review, and require explicit user confirmation. Providers cannot supply scientific numbers, alter equations/data, widen domain bounds, or control animals per tick. Unknown tools/fields and prompt injection fail closed. Keep Groq/Hugging Face optional and retain P3-007 BLOCKED until its persistent spend ceiling is real. No paid calls in this track without authorization.

## Product V4 prompt interpretation (P4-006)

`POST /api/interpret-scenario-lab` accepts exactly `{prompt}` (maximum 1,200 characters). If `LLM_PROVIDER=groq`, the server uses `GROQ_API_KEY` and defaults to `openai/gpt-oss-20b`, which Groq's current public documentation lists as supporting strict JSON Schema outputs. If `LLM_PROVIDER=huggingface`, the server uses `HF_TOKEN` and requires an explicitly configured `HF_MODEL`; model/provider structured-output availability varies and must be verified against the authenticated account. `LLM_MODEL` may override the provider-specific model. Credentials are never returned to the browser.

The adapter asks for only `riose-scenario-lab-intent/v1`, uses a strict schema, temperature 0, output cap 700 tokens, a 12 second timeout and no tool calls. The server parses JSON, applies the existing strict intent validator, and unions any deterministic-parser missing-input or unsupported-request findings. The browser validates again. Provider failures return sanitized errors; the page falls back to its deterministic parser. A per-process per-IP request limiter reduces abuse but is not a persistent or monetary budget. This does not unblock P3-007.

The user prompt remains untrusted content. A provider result only prepares a review draft. The existing separate `Run scenarios` action verifies the approved manifest digest before sending work to the Worker. Version 2 scenario archives retain interpretation source/provider/model and the original validated proposal. If a user edits scenario inputs, the archive records `manual-revision`: it preserves the original proposal, while the manifest binds the inputs actually confirmed and executed. Version 1 archives remain readable.

Current docs: [Groq structured outputs](https://console.groq.com/docs/structured-outputs), [Groq supported models](https://console.groq.com/docs/models), [Hugging Face structured outputs](https://huggingface.co/docs/inference-providers/en/guides/structured-output). Public model support does not prove availability or entitlement for this account.


## Hybrid decision conversation (P4-007/008/009)

`POST /api/decision-assistant` accepts a bounded current prompt, previous user request and optional typed compact completed-result summary. It requests a strict `riose-decision-plan/v1`, independently validated with Ajv and then capability/units/source-number/role/domain/currency validators; the browser repeats semantic checks. No arbitrary tools or scientific output fields exist. A full nullable-key template is required for real Groq compatibility. Missing inputs are determined by the selected local capability, never by unvalidated generated prose.

Groq selects only input drafts, an intent or allowlisted evidence IDs. Registered limitations and numerical result differences are rendered locally. Browser-supplied result summaries are labeled as such and are not authenticated observations. Single, multi-scenario and sensitivity summaries keep their own model/version/units; large sweeps explicitly identify a compact point selection. Revisions prepare review only. Changed inputs discard in-flight replies. Both buttons prevent concurrent interpretation; separate existing confirmation buttons are the sole calculation path. Offline interpretation retains original local-parser assumptions in archives.

Shared provider transport has finite completion caps (700 for the original scenario intent, 1,200 for decision plans), 12 s deadlines, a 64 KiB streamed response bound, no automatic retries, and sanitized HTTP/latency/token metadata. Authentication, schema, timeout, network, quota/rate, invalid and incomplete outputs select an explicit safe fallback. Credentials are only server environment values. The user explicitly authorized the current bounded manual live battery; this does not resolve P3-007's production shared-spend gate.

Laya uses the official non-generative SDK, a pinned multilingual safetensors checkpoint and an isolated CPU process with no credentials/tools. It was evaluated on the frozen bilingual fixture and failed the routing promotion screen. Its local stdin worker is experimental; Product does not dispatch through it. HF authentication and public model acquisition were verified; hosted HF chat inference remains untested. See `hybrid-ai-protocol.md`, the official source audit and `docs/evidence/hybrid-ai-live-validation-2026-10-15.md`.

Single BR-CORTE reports use `riose-br-corte-single-report/v2`, pin registered model version/implementation/evidence, explicitly declare input/output units, and verify canonical content hashes. The reader retains strict v1 compatibility. Opening is non-executing; explicit recalculation compares registered outputs exactly. Residual forage is explicitly a modeled balance, not independently validated forage intake. Existing scenario archive v1/v2 and BR-CORTE comparison/sensitivity contracts are preserved. Compact scenario exports and imports share a 64 MiB guard; invalid imports preserve completed outputs and revoke pending review authority.
