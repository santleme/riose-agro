# Product conversational simulation audit — 2026-10-15

## Checkout and existing product

- Audited the current `main` checkout at `fcd4254` (`origin/main`) and created the task branch `t3code/conversational-population-simulation` from it. GitHub confirmed PRs #185, #186, and #187 are all merged. #185 removed the previous renderer, #186 briefly added a reference scene, and #187 removed that scene and its renderer stack; the current checkout has no farm-scene dependency.
- `product.html` was a redirect to `experiments.html`. The latter is a working form-based experiment page and remains available. Its configured-comparison manifest, worker protocol, replay, run-history storage, exports, and deterministic seed contracts are retained.
- The repository is vanilla ES modules, HTML/CSS, browser Workers, Node server modules, and Rust/WASM. `package.json` pins Node tests and Playwright; no UI framework is needed. Local dependencies were absent at audit time; `npm ci` restored the locked set.
- Existing JS `FarmEngine` starts 1–10,000 identified demo animals, exposes a snapshot, and supports deterministic `tick` calls and four configurable factors (diet, housing, weather, supplement; supplement 0–4 kg DM/head/day). Configured comparison requires exactly one changed factor and returns daily herd aggregates. The Worker can select the native Rust aggregate executor, with JS fallback.
- Population fields already present in JS and Rust are `weight`, `initialWeight`, `energy`, `thirst`, `action`, `patch`, `history`, and global `events`. `patch` is an index into four shared pasture stocks, not a location. Actions come from deterministic clock/rest, thirst-threshold, and housing rules. History stores activity transitions with a reason and observed hour/thirst/housing; it is bounded to 40 records per animal. Global events are bounded to 100. Energy and thirst are engine state indices, not calibrated physiological measures. JS and Rust use the same state shape and transitions; Rust snapshot serde uses camelCase at the boundary.

## Scientific evidence and integration decisions

- BR-CORTE 2023 Eq. 2.6 is available as an explicit model contract and implementation. It computes DMI from body weight, supplement and **supplied ADG** within its stated domain; it does not predict ADG. It is not automatically connected to the demo engine or individual inspector.
- USDA/CPER evidence for young/yearling cohorts is kept separate from mature cow populations. The repository records no eligible adult grazing-cow DMI cohort and a NO-GO for a general DMI prediction baseline.
- Perea grouped-by-animal behavior results are internal classification diagnostics from one cohort; they are not a validated generator for bovine behavior. Engine activity transitions remain deterministic illustrative rules.
- Pasture biomass readiness records a NO-GO for generalizable prediction and distinguishes sampling-point biomass from the engine's paddock stock. No external biomass model is connected.
- Existing uncertainty reports reject calibrated confidence or prediction intervals for these uses. Product reports deterministic deltas only and labels the demo engine unvalidated.
- The repository literature review documents Generative Agents as a human-behavior architecture reference and explicitly rejects extrapolation to bovines. It did not contain detailed evaluations of Social Simulacra, Grounded Agents, or livestock ABMs. A bibliographic spot-check for this audit found Social Simulacra is a social-computing prototype populated with LLM-generated people; “Grounded Agents” is ambiguous, with a relevant Grounded Theory Based Agents study grounding rules in human participants. Cattle/rangeland ABMs such as ECo-Range and ANDES model defined management/environment systems, but they are not evidence for this generic engine. These references motivate explicit agent state/environment/rule provenance only; none is connected or used as biological validation. No LLM takes hourly animal decisions. See [local literature review](../revisao-literatura-simile-agro-2026.md), [Social Simulacra](https://arxiv.org/abs/2208.04024), [Grounded Theory Based Agents](https://doi.org/10.1109/WSC.2012.6465064), [ECo-Range](https://doi.org/10.1016/j.rama.2025.01.003), and [livestock/rangeland ABM review/example](https://doi.org/10.3389/fsufs.2026.1674409).

## V2 implementation boundary

- Product now uses a versioned `riose-experiment-intent/v1` contract and a deliberately narrow deterministic parser. It supports population count, duration, optional breed metadata, weather category and a single supplement comparison, validates the current engine domain, and surfaces missing/unsupported requests. The optional `/api/interpret-experiment` adapter uses configured OpenAI, Groq or Hugging Face credentials only on the server, requests strict JSON, validates against the same experiment contract, and falls back to the local parser when unavailable. The model cannot execute, alter science inputs outside the contract, or return outcome metrics.
- A `populationCompare` Worker command executes both arms from the same initial snapshot/seed with the existing JS engine and retains compact animal states only at days 0, 1, 7, 15, 30, 60, 90, 180 and the final day. Daily aggregate rows are computed in the same pass and checked against `compareConfiguredScenarios` for parity. The bounded activity ring is encoded as numeric tuples and expanded only for the selected inspector animal. Run manifests and the existing local history provide replay; aggregate results and compact observations can be exported as JSON.
- Population execution currently selects the JS engine because the Rust comparison response is aggregate-only. Rust/WASM contracts and existing executor parity are unchanged; extending native output with compact animal observations is future work. This UI labels its executor and does not claim the native Rust runner produced its per-animal timeline.
- The demo snapshot uses seeded generic engine weights and four shared pasture stocks. Breed is prompt metadata only. Heat selects the engine's illustrative weather rules, not a validated heat-stress model. Consumption and cost are aggregate-only; individual intake is unavailable. The retained activity history is bounded and does not record a complete hourly physiology time series.
- Population cells use stable engine IDs and pagination at 1,200 rendered cells. Sorting, activity and direction-of-difference filters apply to returned states; the timeline is restricted to retained points. The visual grid is an observation matrix, never a physical map.
- Aggregate activity counts are calculated from each scenario's recorded activity field at the selected checkpoint. They are counts of engine states, not observed animal behavior.

## Known limitations

- Natural-language coverage is limited to explicit known values and Portuguese/English aliases; unsupported requests are reported instead of guessed. It is not a general language model.
- The generic engine's weight changes are the result of demonstrative feeding/metabolism rules, not validated Nelore predictions. The app must not be used for livestock management decisions.
- A local Node measurement on this checkout, one 30-day pasture supplement comparison, seed `20261015`, JS engine, measured simulation plus compact result serialization: 100 animals = 452.7 ms / 320,472 bytes; 1,000 = 3,867.6 ms / 2,968,811 bytes; 10,000 = 58,289.9 ms / 29,418,246 bytes. The test machine and one run per size are descriptive, not a benchmark claim. A 10,000-animal browser Worker transfer/heap profile remains unmeasured; the 1,200-cell UI pagination limits DOM size, not execution time or result payload.
- Costs use internal illustrative price constants. Pasture stock has no area or measured biomass provenance. Sensitivity, probabilistic uncertainty, and individual DMI are not part of this first Product flow.
- Browser automation depends on a T3 preview host. The current environment reported that no preview automation host is connected; a local headless browser may be used for visual inspection instead.
