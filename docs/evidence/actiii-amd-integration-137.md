# ACT III AMD integration — Issue #137

## Selected workload

The integration routes the existing `FarmEngine.tick` cattle metabolism batch through the AMD service. Each row is one animal in `state.animals` order. The engine already packs each row in `src/client/metabolism-wasm.js` format and has JavaScript and Rust/WASM CPU implementations of the same update.

## Execution contract

- Request contract version: `1`; operation: `livestock_metabolism_batch`.
- Input: `count` animals and exactly `count × 4` finite Float64 values, interleaved as weight (kg), energy (engine scale 0–100), hourly intake (kg dry matter), and resting indicator (zero means active; any nonzero value means resting).
- Output: exactly `count × 2` Float64 values in input order, interleaved as next weight (kg) and energy (engine scale 0–100).
- The workload uses the existing constants and operation order: maintenance `5.3`, gain factor `0.22`, weight floor `200 kg`, and energy clamp `[0, 100]`. No scenario configuration or feeding rules are changed.
- Batch count is `1–10,000`. Invalid sizes, non-finite values, unsupported contract versions, and failed execution return visible errors.
- CPU execution is available in the existing JavaScript/WASM kernel. Product defaults to CPU. When AMD is selected, the Product worker commits a step only after the service reports `backend_used=amd_rocm`; an unavailable service or CPU fallback is shown as an error and leaves the simulation state unchanged.

## Product integration and backend identity

The Product timeline has a `CPU` / `AMD · ROCm` selector. The AMD mode sends the exact batch generated by the current livestock tick through the Product server's `/api/amd/metabolism-batch` proxy to the Python compute service. The service runs PyTorch Float64 tensors on its ROCm device and returns the batch to the worker. Product status reports the actual backend and device after successful execution. The default Product JavaScript path remains CPU; a browser or JavaScript comparison is never labeled as AMD.

Start the local services in separate terminals:

```sh
python3 src/server/compute_service.py
npm start
```

Open `http://127.0.0.1:8000/product.html`, choose `AMD · ROCm`, then advance one hour (or resume the timeline). Successful Product status has the form `AMD · <device name>`. If ROCm is unavailable, Product reports the service/backend error instead of applying CPU results under an AMD label.

For a deterministic parity check against the real Product engine inputs, run:

```sh
npm run verify:amd-livestock
```

The command creates a 24-animal batch from `FarmEngine(seed=2026)`, executes one existing metabolism step on the selected backend, compares all output values against `updateMetabolismJS`, and emits backend/device, input SHA-256, and parity metadata. It exits unsuccessfully if ROCm does not execute or parity exceeds absolute and relative tolerance `1e-12`.

To run the same command against another service URL:

```sh
AMD_COMPUTE_URL=http://127.0.0.1:8766/api/compute/v1 npm run verify:amd-livestock
```

The Node Product proxy can target a non-default service with `COMPUTE_SERVICE_URL`.
